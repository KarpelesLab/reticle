# font.txt - the character generator, drawn.
#
# This is the whole font, and it is the source: tests/apple2.rs reads
# this file, turns it into sw/font.hex and fails if the checked-in hex is
# not what this art says. rtl/apple2_video.v loads the hex with
# $readmemh. Nothing else describes the glyphs, so a reader who wants to
# know what a character looks like on the screen looks here and sees it.
#
# No Apple character generator ROM was consulted, copied or reconstructed
# for this; the shapes below were drawn for this example. See README.md.
#
# Format
#   `glyph <index> <character>` starts a glyph, and the **eight lines
#   immediately after it** are its 7x8 cell, top row first, `#` for a lit
#   dot and `.` for a dark one. Anything not inside those eight lines is
#   ignored, which is what lets this header exist: an art line may well
#   begin with `#`, so "a comment starts with #" would not have been a
#   rule that worked.
#
#   Each glyph is a 5x7 shape in the top-left of a 7x8 cell: the two
#   right-hand columns and the bottom row are the gap between characters,
#   which is why the screen reads as 40 columns rather than as a wall.
#
# The index is the Apple II display code with its two attribute bits
# removed, so glyph 00..1F are ASCII $40..$5F and glyph 20..3F are ASCII
# $20..$3F. That is the order the character generator is addressed in and
# the order the glyphs are in below; `rtl/apple2_video.v` explains how a
# byte in the text page picks one of them and whether it comes out
# normal, inverse or flashing.
#
# A row becomes one byte of sw/font.hex with the *leftmost* dot in bit 0,
# because the video shift register sends bit 0 to the screen first. Bit 7
# is always zero: a cell is seven dots wide.
